PermWorld encoding × architecture development evaluation: read-only code review
Date: 2026-10-10 (America/Los_Angeles)

Scope and status
Reviewed evaluation.py, common.py, training.py, frozen protocol.json, and their
directly reused encoding/core.py and data.py. Frozen code, metrics, and protocols were not modified;
no GPU, training, or repeat validation was run. This is an implementation and interpretation review, not an effect assessment
of development results still running. No pairing/formula issue was found that blocks the current prespecified development evaluation.

1. Shared objects, labels, and training exposure across encodings
Data generate an underlying permutation p only once; each action first computes q=transform(p, action), then
shared labels(q), and finally encodes the same q separately. Both encodings use the same data.npz,
length arrays, label arrays, orbit splits, and batch_indices.npy. Training reads the identity
action in both cases, with identical answer/EOS supervision positions and update budgets; answers are not regenerated by encoding.
Canonical-cycle notation changes the sequence via delimiter replacement and sorting; both encoded lengths are asserted to equal 2*n+4.
Thus this design does not mix in between-encoding sequence-length differences, but encoding effects still include boundary markers, delimiter
identity, and permutation order; they cannot be attributed to just one factor.

This development unit contains only four trained tasks and two evaluation relations: descents–recoils (correct inversion,
wrong complementation) and peaks–valleys (correct complementation, wrong inversion). Saving other labels supports uniform
mathematical construction and does not mean formal confirmation of sixteen tasks and eight relations is complete.

2. Answer stratification and fixed-length evaluation
The selection function's joint key is [length, original left answer, original right answer, right answer under complementation,
and right answer under inversion]; within each fixed length, joint-answer cells with counts at least 3 are retained. Fit/test
masks are generated outside the architecture/encoding/initial-or-trained loop; all conditions
within the same split share masks. Masks do not depend on representations, accuracy, or metric results. Fit/test separately
center using their own label-group means; identical samples or means across splits are not claimed.
Each length is computed separately and aggregated with fixed equal weights; undefined cells must not cause remaining lengths to be reweighted.
This is a ground-truth-based measurement control; it does not remove all confidence, error patterns, or nonlinear
answer information.

3. Decomposition, encoding interactions, and metric direction
B0=initial_correct-initial_wrong; Bt=trained_correct-trained_wrong;
change_correct=trained_correct-initial_correct; change_wrong is analogous;
Delta=Bt-B0=change_correct-change_wrong. Source code checks the latter identity.
Gamma direction is uniformly canonical_cycle-one_line; therefore
GammaDelta=Gammat-Gamma0=Gamma_correct-Gamma_wrong.
CKA, debiased CKA, and neighborhood overlap increase with similarity; held-out Procrustes negates NRMSE
before the same decomposition, so higher reported scores uniformly mean greater similarity, while smaller raw errors are better.
A Delta sign change cannot automatically mean a trained-preference reversal; Gamma0, Gammat,
and both correct/wrong changes must be inspected. Static ground-truth baselines have no initialization learning increment.

4. Input-end position and task-prompt interpretation
The final_norm state at end=2*n+3 is uniformly extracted; the task token is at end+1 and the equals sign
at end+2. Actual evaluation forwards include task and equals suffixes; the measured state precedes them.
The Transformer's causal mask and unidirectional GRU prevent future suffixes from affecting this state. The implemented
independent check compares handwritten prefix-only forwards with caches at a fixed tolerance; this review did not rerun it.
The accurate description is “a state before the task token, causally independent of the current task suffix,”
not “the entire evaluation forward never received a task token.” Each model's weights have already undergone single-task
training; a pre-task state does not mean no task knowledge.

5. Initialization and interpretive scope of architectural comparisons
Each architecture saves genuine step-0, copies it to all tasks and encodings, and checks parameter digests;
paired encodings for a task share dropout starting seeds and batch order. This differs from the grade-C reconstructed initializations
in historical-checkpoint diagnostics, and the two identities must not be conflated. Transformer and
GRU use different initialization seeds and parameter construction, with different parameter counts; the architectural comparison compares these
prespecified systems and cannot separately identify causal effects of architecture, capacity, or initialization families.
The engineering learnability gate does not guarantee matched source accuracies across encodings; encoding learning difficulty can still
affect final geometry. This unit has one new shared data world and is developmental; the 16 models cannot
be treated as 16 independent worlds or a sufficiently powered confirmation experiment.

6. Output baseline and minor documentation issues
output_prob is softmax renormalized over numeric-answer tokens 0..30; it is not
the full-vocabulary probability distribution and does not preserve total numeric-answer mass. The paper should use this name and
scope interpretation consistently; it cannot exclude all output-related information.
The batch_schedule text in protocol.json inherited “all32 models”; the actual current
manifest is 4 tasks × 2 encodings × 2 architectures = 16 models. Code reads the same saved schedule;
no exposure difference caused by this textual leftover was found. Frozen files need not be recomputed for wording; the final
report should state 16 models, and later protocol versions may correct the documentation leftover.
