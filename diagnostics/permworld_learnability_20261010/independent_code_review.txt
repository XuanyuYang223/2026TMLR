已核实的实现

1. 目录隔离：新 ROOT 固定为 /mnt/yangx-projects-f/20261010/permworld_learnability。新 setup 仅读旧协议、冻结清单和受保护产物，写新 ROOT 与新诊断目录。复用的 model()/generate_world()/atomic_checkpoint() 不调用旧 setup/initial/world 写入器。training 的输出 resolve 后必须位于新 ROOT；工程覆盖只允许 ROOT/engineering。源模型只从固定 manifest 查找。

2. 历史排除：先校验旧历史索引与旧 archdev 数据 archive 的 SHA，再追加旧开发 train/validation/test 每个 anchor 的全部八成员轨道。候选新数据使用同一个冻结 orbit()；任何轨道成员出现在历史索引中都会拒绝，非八成员轨道也拒绝。新世界 train/validation/test 的轨道代表分开记录并检查无交集。这个结论依赖此前完整历史索引审计；本审查没有重新枚举所有旧训练语料。

3. 数据与预算相同：固定 n10、11、12，train 2048/长度、validation 1024/长度；两编码使用同一底层排列、答案、轨道拆分和已保存 8000×64 batch schedule。生成器每三更新随机排列三长度，所有模型复用同一 schedule。2048×3、batch64、8k 对应每模型约83.3次平均训练集遍历；这是一次组合开发改变，不是仅改编码。

4. 真实初始化：每架构有新构造器真正输出的 step0.pt，参数与 RNG 保存；两编码和四性质从同一该架构参数值加载，训练入口与 CPU 检查均重新计算 parameter_hash。初始化 checkpoint、初始参数、协议、源版本、数据和起始 RNG 都绑定到恢复 checkpoint。两架构没有相同权重身份的主张。

5. 答案监督：复用已冻结 batch/loss 的因果移位。CPU 检查独立比较 answer 与 EOS 两位置的 CE，检查其他位置无梯度，并比较全序列与仅 prompt 的答案 logits。训练/验证答案指标使用完整词表 argmax；数字限制内准确率另列，EOS 是真实答案 teacher-forced 指标，不能替代答案学习。

6. 门槛：协议固定8k终点，每模型逐长度等权答案均值≥90%、最弱长度≥85%、相对训练长度众数≥20pp、EOS≥99%；同task×architecture两编码均值与每长度差均≤5pp。门槛只依据 identity validation 答案/NLL，固定一个候选，不使用 Γ/Δ/CKA，也不读测试成绩选择配置。报告实现仍须独立 fixture 验证等权、训练众数来源与不完整终点不能通过。

7. 恢复检查：每 architecture×encoding 有真实连续 0→32 与另进程 0→16→32；比较参数、optimizer 与 RNG。工程输出与源模型目录分离，不能预更新源模型。预算造成不足32更新时已改为显式 budget_exhausted，不冒充 RNG/参数不一致。连续参考若已经存在而没有完整 result，会拒绝偷偷续跑；意外工程进程中断后的重试需明确处理参考身份，不能伪造一个“连续”参考。

8. 两小时：driver 创建一次持久 start/deadline，恢复不重置；stop_updates_epoch 为 deadline−30s，cutoff 后不启新 job。training 每更新检查 cutoff；验证入口与每 batch、实际 forward 之前都要求至少5s余量。验证不足则 None 且 validation_missing_due_to_budget=True，不用不完整分数。截止后只安全保存状态；CPU tree 序列化避免以完整 GPU 验证作为“另外计时的清理”。最终 GPU batch 的实际耗时与保存开销仍需运行审计，不应把纸面防护当作严格零超时证明。

9. 完成身份：completed.json 仅 source output=None、真实step8k且完整validation时写。工程覆盖即使请求8k也不能创建source完成文件。driver按固定 manifest 的 run_id、step8000、协议、source版本与data SHA核对完成，而非直接数任何工程文件。partial2k/4k/实际中断更新不能替代8k终点。完成数与是否通过学习门槛是两个字段，不应混用。

10. 耗时解释：新 driver 记录共享实际 wall clock，旧并发每模型 loop elapsed 的总和不是本机实际 GPU 小时。旧吞吐只能作为代理，不决定新的“已用GPU小时”；串行新运行的实测时间、恢复工程和验证都纳入共同预算。持久 epoch 截止还会包含进程暂停时的空闲，是保守约束，不是精确 GPU kernel 利用率统计。
