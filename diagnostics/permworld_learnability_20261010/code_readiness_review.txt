Verified: no new training blocker found
1. In batch, END=2n+3, task=END+1, equals=END+2, answer=END+3,
   and EOS=END+4. Targets are non--100 only at answer/EOS; after shifting loss, the equals
   position predicts the answer and the answer position predicts EOS. Current numeric vocabulary 00..99 IDs equal
   the integers, so accuracy correctly compares numeric truth. Existing CPU gradient-position checks,
   independent hand-calculated two-term CE, and future-answer causal checks passed and are not repeated.
2. The same permutation receives shared exact labels before separate encoding; cycle encoding does not recompute
   labels differently. Cycle traversal direction is p[current-1], consistent with the one-line permutation used by the mathematical properties.
3. Singleton cycles are retained, with commas within cycles and semicolons between cycles; both boundary markers are explicit.
   n numeric tokens plus n-1 delimiters retain sequence length 2n+4; semicolons do not lengthen the sequence or
   lose cycle closure. Closure points from the last element back to the first in the same cycle through the canonical sequence,
   not an additional output token. Decoding requires each cycle's smallest value first and cycles sorted by first value,
   then checks re-encoding; cycle sequences are not mistakenly treated as one-line numeric lists for labels.
4. Maximum training width 2*30+8=68 is below max_seq_len=128. Position embeddings and
   masks are long enough. The Transformer's boolean allowed mask agrees with SDPA semantics;
   GRU propagates only from the past, so trailing PAD states cannot change earlier valid tokens.
5. Each training update uses one length, with balanced permutation cycles over 21 lengths; batch64, 4
   micro16 batches, answer/EOS once per sample, loss divided by4 for accumulation.
   Both encodings share indices, initialization, and same-task starting RNG. Warmup and cosine use global
   step; full optimizer/RNG/step states are saved, and existing resume checks passed.
6. BF16 autocast uses FP32 parameters, with explicit finite-loss/total-gradient-norm checks; step0
   and final parameter digests differ. All existing 16 overfitting checks with 48 samples/4 answer classes passed.
   This excludes simple answer-position misalignment, EOS-only supervision, or no parameter updates,
   but does not prove complete rules learned for new inputs.

Observed learning stagnation (existing curves only)
Cycle Transformer/GRU descents validation is approximately .279 at1k and .310/.314 at20k; peaks
reach approximately .407 at2k and .408/.417 at20k. EOS is1 from1k, and numeric/full-vocabulary
answer accuracies agree. Difficulty lies in numeric answers, not nonnumeric-token outputs or EOS failure.
train_loss records only answer+EOS combined CE for the current update; its length changes,
so fluctuation is neither whole-training loss nor enough alone to establish optimization divergence.

More specific candidate: changed task algorithms, not longer sequences
One-line descents directly compare adjacent p(i),p(i+1), and peaks/valleys adjacent triples. Cycle notation
requires identifying each value's cycle successor, including cycle-end backreferences, then reassembling p(i) by numeric
index before comparing adjacent coordinates. Adjacent original-sequence tokens generally are not adjacent
input coordinates. Recoils additionally need adjacent-value positions in the inverse permutation; this is nonlocal even in one-line notation.
These are mathematical changes in computational requirements, not verified neural-mechanism explanations.

Numeric tokens use embeddings without numerical priors; fixed absolute positions describe cycle-sequence
positions, not permutation coordinates directly. Only the final two tokens are supervised, with no
intermediate mapping/counting supervision. GRU must also retain these relations in one terminal state;
Transformer can access the prefix directly but still must learn composed indexing/successor/comparison operations.
Stagnation in both architectures cannot be attributed only to GRU memory length or prove inexpressibility of either model family.

20k updates=1,280,000 sample exposures, divided over 21 lengths with only952/953 updates per length;
each of4096 training objects per length is seen approximately14.88 times. Mixed-length training and global LR decay may provide
insufficient optimization opportunity; dropout, learning rate, and loss allocation are also untested candidate factors.
Declining equal-weight answer+EOS combined CE may hide answer stagnation; answer CE must be separate.

Reusable historical interfaces
- core.encode/decode/labels, TOKEN_TO_ID/TASKS: pure mathematics and encoding interfaces;
  core.batch(prefixes, ns, task, answers, device) and core.loss(logits,target)
  retain answer supervision without changing vocabulary or labels.
- core.make_model(config,seed)+longrun_attention.accelerate; common.CausalGRU
  Or common.model(config,architecture,seed,device): constructs fresh models. model
  resets Python/NumPy/Torch RNG, so fix training/dropout starting RNG again afterward.
- Original accuracy logic is reusable, but new development should separately save per-length full-vocabulary/numeric answer accuracy,
  answer CE, EOS CE, and combined CE rather than treating the final minibatch loss as overall loss.
- Do not directly call historical setup/initial/run_job/child/source_version: they hard-code
  ROOT/CONFIG, checkpoint-output paths, and fixed8e5 historical counts, and write/verify old experiment directories.
  New driver, initialization, protocol, data, and stage artifacts must use a new independent root.
- generate_world's original width64/maxn30 can be reused, but short lengths cannot blindly retain4096 samples
  and “eight-member orbits only.” Small S_n can lack capacity or contain no eight-member full orbits, exhausting
  fixed rejection sampling. Short-length development must explicitly freeze feasible counts/exclusion rules;
  never silently relax historical/orbit exclusion or automatically change lengths.

New development checks (without repeating old checks)
1. Verify genuine step0 copies, parameter updates, global step/LR
   restoration, and data/schedule/protocol/source hashes only for the new driver/config interface; stage restoration must not reset cosine.
2. Only changes to masks/loss families/encoding/optimizers require new hand calculations and small-sample
   checks for changed components. Separate answer/EOS CE and aggregate by sample count, validating identity train/validation inputs only.
3. Determine and fix per-length answer-mode/probability baselines from training data; use only validation answer
   accuracy, answer CE, and gains over that baseline for configuration choice. Initialization often outputs nonnumeric tokens,
   so “accuracy improvement>.10” is only an engineering gate, not a standard for content learning.
4. Fix a few configurations and2k/4k/8k stages, recording actual training exposure/cost; encodings share
   data/update budgets. Use only training/validation, not test/CKA for selection. Development selection
   is excluded from confirmation; if all configurations stagnate, report under prespecified stopping rules without automatic scaling.

Documentation leftovers and potential porting risks
Historical protocol batch_schedule says “all32 models,” but there are16. Code reading the same
schedule did not create exposure differences. New driver should state16 rather than inherit the wording.
Current accuracy compares argmax token IDs to integer labels correctly only because numeric IDs equal integers;
new vocabulary order requires explicit mapping. This is not a current bug. Historical load_data/prepare
fixed counts apply only to the old world and would mis-validate a direct port; new worlds require independent audits.
No engineering issue requiring unfreezing old results was found. Candidate causes above need new validation learning data,
rather than interpreting low cycle accuracy as a representational mechanism before testing.
